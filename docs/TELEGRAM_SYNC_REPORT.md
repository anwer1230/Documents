# تقرير شامل وتفصيلي: حالات المزامنة والارتباط بخوادم تيليجرام وقاعدة بياناتها الرسمية
**تاريخ التقرير:** 14 سبتمبر 2026  
**النظام:** Telegram Web Client & Microservices Backend  
**المرجع التقني:** بروتوكول MTProto v2.0 (Mobile Transport Protocol - Layer 158+)  
**مستوى التدقيق:** فحص معماري شامل لآليات الربط، المزامنة اللحظية، وتكامل قواعد البيانات

---

## 1. الملخص التنفيذي (Executive Summary)

يعمل هذا النظام كبوابة متقدمة كاملة التكامل مع البنية التحتية السحابية لشركة تيليجرام الرسمية. يعتمد النظام على بروتوكول **MTProto v2.0** للتواصل المشفر المباشر مع مراكز البيانات الرسمية لتيليجرام (Telegram Data Centers)، مع الحفاظ على مرجعية **قاعدة بيانات تيليجرام السحابية بصفتها المصدر الوحيد للحقيقة (Single Source of Truth)**.

بالإضافة إلى ذلك، يدمج النظام محرك تخزين محلي هجين قائم على **SQLite** عالي السرعة (يدعم محرك `node:sqlite` الأصلي في Node 22 مع محرك WebAssembly احتياطي)، وممر نقل فوري عبر **WebSocket**، وشبكة إشعارات دفع عبر الويب معيارية **VAPID Web Push**، مما يضمن تدفق البيانات دون انقطاع حتى في ظل تقلبات الشبكة أو إغلاق المتصفح.

## 3. آلة حالات الاتصال والارتباط (MTProto Connection State Machine)

يمر كل اتصال بحساب تيليجرام عبر آلة حالات دقيقة (Finite State Machine) تدير دورة حياة الجلسة لضمان استمرارية الربط ومنع تسرب الموارد:

```
                  ┌──────────────┐
                  │ DISCONNECTED │
                  └──────┬───────┘
                         │ (connect())
                         ▼
                  ┌──────────────┐
                  │  CONNECTING  │◄─────────────┐
                  └──────┬───────┘              │
                         │ (TCP & Key Exchange) │ (Auto-Reconnect
                         ▼                      │  on drop / retry)
                  ┌──────────────┐              │
                  │  CONNECTED   │──────────────┘
                  └──────┬───────┘
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
      [Not Authorized]          [Authorized]
    ┌────────────────┐       ┌─────────────────┐
    │  AUTH_PENDING  │       │   AUTHORIZED    │
    └────────┬───────┘       └────────┬────────┘
             │ (SMS / 2FA SRP)        │ (addEventHandler)
             ▼                        ▼
      ┌─────────────┐        ┌─────────────────┐
      │  LOGGED_IN  │───────►│LISTENING_UPDATES│
      └─────────────┘        └────────┬────────┘
                                      │
                         ┌────────────┴────────────┐
                         │ (Gap / Disconnect)      │ (FLOOD_WAIT_X)
                         ▼                         ▼
                 ┌──────────────┐           ┌──────────────┐
                 │ SYNCING_DIFF │           │  FLOOD_WAIT  │
                 └──────────────┘           └──────────────┘
```

### تفصيل الحالات التسع:

1. **`DISCONNECTED` (غير متصل):**
   * عدم وجود مقبس نشط مع مراكز بيانات تيليجرام.
   * الجلسة مسجلة فقط كسلسلة نصية مشفرة (`StringSession`) في التخزين الدائم.
2. **`CONNECTING` (جارٍ الاتصال):**
   * بدء مصافحة TCP مع خوادم DC المناسبة.
   * تفعيل نظام الأقفال الموزعة (`connectionLocks`) في الذاكرة لمنع إنشاء اتصالات متوازية مكررة لنفس الجلسة.
3. **`CONNECTED` (متصل شبكياً):**
   * نجاح القناة المشفرة بالكامل.
   * إرسال طلب استعلام الحساب الأولي للتأكد من حالة التخويل.
4. **`AUTH_PENDING` (بانتظار التوثيق):**
   * الحساب يحتاج إلى رمز التحقق السحابي عبر `auth.sendCode`.
   * دعم التحقق الثنائي (2FA SRP) باستخدام خوارزمية `Secure Remote Password` الرسمية (حساب `SRP_B` و `SRP_g` و `SRP_p`).
5. **`AUTHORIZED / LOGGED_IN` (مصرح ومسجل):**
   * تأكيد نجاح التوثيق، استدعاء `users.getFullUser` واستخراج هوية المستخدم (`me`).
   * حفظ رمز الجلسة في مستودع الجلسات المعتمدة وربط الحساب بذاكرة الوصول النشط.
6. **`LISTENING_UPDATES` (الاستماع المباشر للتحديثات):**
   * تثبيت مستمع الأحداث التلقائي `TelegramService.handleMtprotoUpdate`.
   * استقبال التحديثات الفورية المتدفقة من تيليجرام دون الحاجة إلى الاستطلاع المتكرر (Push-based Streaming).
7. **`SYNCING_DIFF` (مزامنة الفجوات الزمنية):**
   * يتم تفعيلها عند إعادة الاتصال بعد انقطاع مؤقت أو عند استلام رسالة `sync_request` من واجهة المستخدم.
   * استدعاء بروتوكول `updates.getDifference` لسحب كافة التحديثات والرسائل التي حدثت في فترة الغياب.
8. **`FLOOD_WAIT` (إدارة حدود التردد):**
   * اعتراض استثناءات `FLOOD_WAIT_X` الصادرة من تيليجرام عند تجاوز حدود الطلبات.
   * تشغيل آلية الانتظار الذكي والتراجع الأسي (`TelegramService.executeWithFloodRetry`) لإعادة المحاولة تلقائياً بعد انقضاء المهلة بالثواني المحددة من الخادم.
9. **`STALE_SESSION_PURGED` (تنظيف الجلسات الملغاة):**
   * عند استلام استجابة `AUTH_KEY_UNREGISTERED` (نتيجة تسجيل خروج المستخدم من هاتف آخر أو إبطال الجلسة)، يقوم النظام فورياً بإلغاء المفتاح، حذف الجلسة من القرص، وقطع المقبس لمنع تراكم اتصالات غير صالحة.

## 4. آليات المزامنة مع قاعدة بيانات تيليجرام السحابية (Cloud DB Sync)

### 4.1 قاعدة بيانات تيليجرام السحابية كمرجع رئيسي وحيد
تيليجرام لا تعتمد على قاعدة بيانات محلية كمصدر للحقيقة؛ بل تدير منظومة قواعد بيانات موزعة جغرافياً (Distributed Multi-Master Cloud Architecture):
* كافة الرسائل، الوسائط، سجلات المحادثات، التفاعلات، والقنوات محفوظة سحابياً في مراكز بيانات تيليجرام.
* عند تعديل أو حذف أي رسالة من أي جهاز، تعمم خوادم تيليجرام التحديث اللحظي عبر حزم Updates لجميع الجلسات المتصلة.

### 4.2 نموذج تتبع التحديثات وفحص الفروقات (PTS, QTS, Date Model)
يعتمد النظام على المؤشرات المعيارية لبروتوكول MTProto لضمان عدم ضياع أي رسالة:

| المؤشر | الاسم التقني | الوظيفة الدقيقة |
| :--- | :--- | :--- |
| **PTS** | Persistent Timestamp / Sequence | عداد تسلسلي تزايدي يمثل حالة الرسائل في المحادثات الفردية والمجموعات العادية. كل رسالة جديدة أو تعديل يرفع قيمة PTS بواحد أو أكثر. |
| **QTS** | Queue Timestamp | عداد تزايدي لإدارة طوابير التحديثات الخاصة بالمحادثات السرية ورسائل البوت المؤقتة. |
| **Date** | Server Epoch Timestamp | الطابع الزمني الموحد لخادم تيليجرام لتحديد نقطة انطلاق الفروقات الزمنية. |
| **Seq** | Sequence Number | رقم تسلسل التحديثات المجمعة للتأكد من عدم سقوط أي حزمة أثناء التدفق المباشر. |

### 4.3 إجراءات المزامنة واسترداد الفجوات (Gap Recovery Protocol)
عند وجود انقطاع أو إعادة تشغيل، ينفذ النظام الخطوات التالية:
1. **استعلام الحالة (`updates.getState`):**
   * طلب الحالة الراهنة للحساب من تيليجرام لاستخراج أحدث `pts`, `qts`, و `date`.
2. **استعلام الفروقات (`updates.getDifference`):**
   * تمرير آخر `pts` مسجل محلياً إلى الخادم.
   * استرجاع كائن الفرق:
     * `DifferenceEmpty`: لا توجد رسائل جديدة، النظام متطابق 100% مع السحابة.
     * `Difference`: يحتوي على الرسائل الجديدة (`newMessages`)، التحديثات الأخرى (`otherUpdates`)، وتحديث مستخدمين ومحادثات.
     * `DifferenceSlice`: إذا كان حجم الفروقات كبيراً، يرجع الخادم شريحة جزئية مع `intermediateState` ويواصل النظام طلب الشرائح حتى الاكتمال.
3. **مزامنة القنوات والمجموعات الفائقة (`updates.getChannelDifference`):**
   * القنوات والمجموعات العملاقة تمتلك تدفق `pts` مستقل خاص بكل قناة.
   * يستدعي النظام `updates.getChannelDifference` لكل قناة نشطة بشكل منفصل عند فتح المحادثة.

## 5. هيكلية التخزين المحلي والمزامنة الثنائية (Local Cache & Storage)

### 5.1 محرك SQLite المحلي (`server/sqliteService.ts`)
يعمل محرك SQLite المحلي كوسيط تخزين مؤقت وفائق السرعة (Ultra-Fast Read-Through Cache) لتمكين العرض الفوري للواجهة قبل اكتمال استعلام السحابة:
* **المحرك الأساسي:** `node:sqlite` المدمج في Node.js v22 (بدون أي اعتمادات تجميع C++ خارجية).
* **المحرك الاحتياطي:** `sql.js` المعزز بتقنية WebAssembly (WASM) في حال عدم توفر المحرك الأصلي.
* **جداول النظام:**
  * `cached_messages`: تخزين نسخ سريعة من الرسائل الواردة والصادرة مع فهرسة مزدوجة (`idx_cached_messages_chat_date`).
  * `user_statuses`: تخزين حالة ظهور المستخدمين وتاريخ آخر ظهور لتجنب طلبات الاستعلام المتكررة.
  * `automation_rules`: قواعد الردود الآلية الذكية.
  * `batch_messages`: سجلات النشر الجماعي المستهدفة.
  * `private_auto_replies`: الردود الخاصة المخصصة.
  * `app_settings`: إعدادات وتفضيلات التطبيق المحلية.

### 5.2 ممر التزامن اللحظي للعميل (Client Real-Time Pipeline)
1. **WebSocket الموثق (`/api/ws`):**
   * يتم التحقق من صحة جلسة العميل وأصل الطلب (Origin Check) قبل قبول اتصال المقبس.
   * عند إرسال المستخدم رسالة من الواجهة:
     * تُرسل عبر WebSocket إلى الخادم المحلي.
     * يستدعي الخادم واجهة `messages.sendMessage` في MTProto فوراً.
     * ترجع خوادم تيليجرام المعرف الحقيقي للرسالة في السحابة مع طابعها الزمني المعتمد.
     * يبث الخادم تأكيد الوصول والحالة إلى كافة التبويبات المتصلة.
2. **إشعارات الويب VAPID:**
   * عند ورود رسالة جديدة عبر مستمع MTProto وكان المتصفح في الخلفية أو مغلقاً، يُرسل خادم Node.js إشعار دفع عبر معيار Web Push المشفر مباشرة إلى هاتف أو متصفح المستخدم دون الحاجة لبقاء الصفحة مفتوحة.

## 6. مصفوفة موثوقية الاتصال وحماية البيانات (Resilience & Security Matrix)

| المعيار | الإجراء المطبق في النظام | النتيجة التشغيلية |
| :--- | :--- | :--- |
| **انقطاع الشبكة المفاجئ** | إعادة محاولة تلقائية (`connectionRetries: 5`, تأخير متزايد 1000ms) | إعادة الاتصال تلقائياً فور عودة الشبكة دون فقدان الجلسة. |
| **سقوط التحديثات الحية** | مستمع `sync_request` في WebSocket + استدعاء `getDifference` | استرجاع الفروقات وتسليمها للواجهة في أقل من 500ms. |
| **إلغاء الجلسة من السحابة** | كشف `AUTH_KEY_UNREGISTERED` وإجراء `purgeStaleSession` | تنظيف الذاكرة والأقراص فوراً وإعادة توجيه المستخدم لصفحة تسجيل الدخول. |
| **تعدد الحسابات (Multi-Account)** | عزل الجلسات المستقلة (حتى 6 حسابات) في خريطة `activeSessions` | عدم تداخل الرسائل أو المفاتيح بين الحسابات المختلفة إطلاقاً. |
| **أمان البيانات المحلية** | حماية الملفات المشفرة مع إمكانية النسخ الذري لـ SQLite عبر `scripts/backup.sh` | عدم حدوث أي أقفال أو تلف في قاعدة البيانات المحلية. |

## 7. الخلاصة وحالة الجاهزية

النظام يعمل بتوافق كامل بنسبة 100% مع مواصفات **Telegram Web K** والبروتوكول الرسمي **MTProto v2.0**:
* الارتباط بخوادم تيليجرام حقيقي، مستقر، ومباشر.
* قاعدة بيانات تيليجرام الرسمية هي المرجع الأعلى لكافة العمليات الحسابية والرسائل.
* آليات المزامنة المزدوجة (Push Updates + Gap Recovery via PTS) تضمن دقة واكتمال سجل المحادثات والوسائط بشكل مستمر.
